# 后端待办（给 Codex）：客户端事件 → 管理端通知

更新：2026-11-11 ｜ 来源：客户删除项目后，管理端铃铛应有通知

## 一、为什么是后端

前端只能决定“点删除时调哪个接口”。通知要有收件人、要落库、要跨设备可见，还必须在客户端绕过页面直接调接口时也成立——所以生成通知这件事只能在服务端做。

前端现状（不用改）：

- `NotificationBell` 已经存在，读 `GET /api/notifications`
- 管理端（`isAdmin`）与客户端共用同一个铃铛组件
- 客户端删除项目已经调用 `DELETE /api/business/projects/:id`

## 二、必须做的一条

**客户删除项目 → 管理端收到通知**

- 触发：`DELETE /api/business/projects/:id` 成功
- 收件人：管理员（`isAdmin` 角色），或该项目的负责人
- 内容：谁删的、项目名、删除前状态、时间
- 点击：跳到管理端该项目（已删除则至少看到项目名与删除记录）
- 已删除的项目不应再出现在通知的“打开项目”里，链接要么指向已删除详情，要么指向操作记录

验收：

1. 客户删除一个未付款项目
2. 管理端铃铛出现未读红点，1 分钟内可见
3. 点开能看到“XX 删除了项目《YY》”
4. 标记已读后红点消失，刷新仍已读
5. 客户端直接调 `DELETE` 接口（不经页面）也产生通知

## 三、建议一起做的（同一套机制）

| 事件 | 收件人 | 说明 |
|---|---|---|
| 客户删除项目 | 管理员 / 负责人 | 本次需求 |
| 客户新建项目并提交 | 管理员 / 负责人 | 接单提醒 |
| 客户完成付款 | 管理员 / 财务 | 到账提醒，含金额 |
| 客户签署合同 | 管理员 / 负责人 | |
| 客户确认问卷 | 管理员 / 负责人 | 可以开始投放 |
| 客户验收报告 | 管理员 / 负责人 | 项目可归档 |

## 四、数据与接口建议

```
Notification {
  id, type,            // PROJECT_DELETED / PROJECT_CREATED / PAYMENT_RECEIVED ...
  actorUserId, actorName,
  projectId, projectTitle,
  title, body,
  createdAt, readAt,
  link                  // 前端路由，例如 /admin/business-projects?project=<id>
}
```

- `GET /api/notifications`：按角色返回，管理端只看管理端事件
- `PATCH /api/notifications/:id/read`
- 保留期与去重：同一项目同一事件只生成一条

## 五、前端已知的点（供对齐）

- 铃铛组件已有未读数与已读逻辑，只等后端返回数据
- 管理端路由：`/admin`、`/admin/business-projects`
- 客户删除项目的入口：项目卡「•••」菜单与悬停面板，未付款状态可见
