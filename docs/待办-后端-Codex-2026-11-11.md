## P0 · 打通客户流程（三个接口）

前端已在卡片和详情里放了入口，调用的是真实接口，未实现时返回 404，页面提示“这一步还没开通”。

| 方法 | 路径 | 由谁触发 | 前置状态（后端必须校验） | 成功后 |
|---|---|---|---|---|
| POST | `/api/business/projects/:id/contract/sign` | 客户 | `CONTRACT_SENT` | `CONTRACT_SIGNED`，可进入付款 |
| POST | `/api/business/projects/:id/questionnaire/client-approve` | 客户（**仅定制线**） | 已付款 + 问卷 `PENDING_REVIEW` | 问卷 `APPROVED`，可投放 |
| POST | `/api/business/projects/:id/accept` | 客户 | 已交付/已完成 + 报告已放行 | `ACCEPTED`（终态） |

要点：

- 自助线（`serviceCategory = SURVEY`）**没有**客户确认问卷这一步：付款后客户直接发布。后端不要要求自助线走 approve。
- 三个接口都要 `POST` 幂等（重复点不产生第二条记录）。
- 每次状态变更写操作日志（谁、何时、从什么状态到什么状态）。

## P0 · 收款

1. **金额一致**：`POST /api/business/projects/:id/payment` 实际扣款必须等于前端报价页展示的合计。前端价格来自 `content/rateCard.js`；如果后端有自己的定价，请返回一份 `quote` 给前端展示，或让前端改为读后端报价。
2. **余额支付**：从余额扣款成功时，返回的 `payment.status` 要让前端识别为已支付（`PAID / SUCCEEDED / COMPLETED / CAPTURED` 之一），不要只返回 201 空对象。
3. **支付链接**：需要跳转时返回 `payment.checkoutUrl`；不需要跳转就直接置 `FUNDED`。
4. **PayPal 回跳**：目前回跳调的是 `/api/business/account/recharge/paypal/return`（充值）。项目付款的到账必须以 **webhook** 为准落到 `FUNDED`，不能依赖回跳。
5. **幂等**：前端带 `X-Idempotency-Key: business-payment:<projectId>`，重复请求不能重复扣款。

## P0 · 权限（越权）

前端只做路由守卫，越权完全靠后端。

必须逐条测：

- [ ] A 的 token 请求 B 的 `projectId` → 403/404
- [ ] A 的 token 拉 B 的问卷结果 `/questionnaire/responses`
- [ ] A 的 token 下载/导出 B 的报告或 CSV
- [ ] A 的 token 调 `PATCH /report` 放行 B 的报告
- [ ] 客户端 token 调管理端 `/api/admin/**` → 403
- [ ] 公开问卷 `/api/business/public/:id` 只能读该问卷，不能枚举其它

## P1 · 状态机语义

1. **报告放行**：`APPROVED` 与 `SENT` 都算“已放行”（前端 `isReportReleased` 两者都认）；撤回走 `PATCH /report` 传 `REVOKED`。
2. **删除**：客户只能删未付款项目（`DRAFT / SUBMITTED_FOR_REVIEW / QUOTE_REQUIRED / QUOTE_SENT / CLIENT_ACCEPTED / CONTRACT_SENT / CONTRACT_SIGNED`），已付款及之后一律拒绝。前端已按这个规则隐藏按钮，后端必须同样校验。
3. **状态跳变**：见 `docs/流程审计-项目状态机.md`，前端不保证顺序，后端必须拒绝跳步。
4. **问卷状态**：`DRAFT / PENDING_REVIEW / APPROVED / PUBLISHED / ARCHIVED`；`PUBLISHED` 才允许回收；已发布不可改结构。
5. **配额**：前端只负责配置，回收时按配额拦截，满了返回 `QUOTA_FULL`（前端已处理这个错误码）。

id, title, status, serviceCategory, studyFormat, createdAt, updatedAt,
