目标是重设计视频 Hero 之后的第二页入口区，让新闻、调查与未来社区入口的层级、文案和转化路径更清晰。

### 第十阶段后续：研究社区的定位与落地顺序

**平台定位（内部）**

- 用户侧始终说清楚四件事：有什么可参与、是否适合我、要花多久、完成后得到什么；避免把“研究社区”“成员库”等机构术语直接丢给用户。
- 机构侧以后才提供研究项目、样本匹配与洞察交付。平台的价值是把合适的研究机会与愿意参与的人连接起来，而不是一开始同时做新闻媒体、社交网络、研究公司和活动公司。
- 当前可继续用已有的外部问卷机会维持用户侧供给；自有研究先从范围小、目标明确、已确认奖励来源的项目开始，不先承诺无法兑现的活动或奖励。

**画像与选择性开放**

- 注册画像现在只补齐地区/语言、年龄段、关注主题和愿意参与的形式；不再重复收集已有答案。
- 机会应按地区、语言、主题和参与形式筛选后再展示。用户看不到不适合自己的项目是正常产品行为，不应把所有项目都展示成“可参加”。
- 城市、详细住址及其他敏感信息只在某个具体研究确有资格筛选需要时，再单独说明用途并征得同意。

**五个社区入口的真实含义**

1. `最新简讯`：编辑发布的项目动态、已公开的结论或平台公告；不是自动堆砌的新闻流。
2. `参与活动`：展示可报名的在线问卷、访谈、小组或线下活动，必须写明主题、形式、预计时长、奖励、地区/设备要求和截止时间。
3. `讨论`：围绕一条由团队发起、有人维护的问题发表评论；先做受控讨论，不急着开放无限制评论区。
4. `提出一个主题`：用户提交想研究的问题或本地观察，进入审核队列；它是选题来源，不承诺一定立项，也不是对外募资入口。
5. `研究综述`：只发布可公开的匿名汇总、方法说明和结果摘要；项目方专属结果与公开内容必须分开。

**新闻墙与公开结果**

- 新闻墙中的 `News Signal` 只问“这件事是否值得进一步研究”，回答是一个选题优先级信号，不是判断新闻真伪或对错。
- 默认仍优先展示 UTC 当天的新闻；若上游当日没有可用条目，则改为显示最近 48 小时的已验证新闻，并在界面明确标为 `Latest available`，不能将旧内容伪装为当天发布。
- 当前详情页只提供“Worth researching”这一正向信号；保存后不公开票数或生成结论，保留给编辑进行后续主题归并。
- 当同类信号积累后，编辑可将其归入主题，决定是否发起讨论、短问卷或公开综述；没有足够信号时不制造“研究结论”。
- 每个项目的输出必须有可见性：`公开`、`仅项目方` 或 `仅进度通知`。对外发布前确认已匿名化且获得发布许可。

**下一阶段的最小后端路线（按顺序）**

1. **机会匹配与报名（下一步）**：建立“研究机会”数据、资格条件和用户报名状态。用户只看见与自己画像匹配的机会，报名后显示“已申请 / 已入选 / 未入选 / 已完成”。
2. **活动运营基础**：为机会补齐奖励、截止时间、参与方式、名额和通知状态；先支持人工创建和人工审核，不急着自动化复杂调度。
3. **最新简讯与公开综述**：建立可编辑的内容条目和可见性控制，再把真实的项目进度与已获准公开的结果呈现出来。
4. **受控讨论与主题投稿**：先做审核、状态反馈和举报/隐藏能力，再考虑奖励、公开评论或自动发布。
5. **机构侧工作台（最后）**：当机会发布、匹配、报名、完成和结果交付已经跑通并可重复后，再建设机构账户、项目创建、样本筛选和报告交付。

**日常运营闭环（大白话）**

1. 找到一个真实需要回答的问题，并确认谁负责项目、奖励和结果范围。
2. 写清楚招募卡片，让合适的人报名；不合适的人不打扰。
3. 审核报名、确认参与、记录完成与奖励状态。
4. 向参与者说明结果进度；能公开的做成简讯或综述，不能公开的只发项目进度。
5. 复盘哪些主题、地区和参与形式有人响应，用这些信息改进下一次招募。

外部社群可作为公告、答疑和召回渠道，但不能替代站内同意、资格、报名、奖励和研究记录。所有用户文案保持具体，优先使用“报名活动”“分享看法”“查看进度”“阅读公开结果”等直白说法。

### 第十四阶段：客户报价、启动闸门与角色通知（已完成并发布）

- Business 项目现在按正式商业阶段流转：`Draft → Submitted for review → Quote required → Quote sent → Client accepted → Funded → Recruiting → Live → Completed`。阶段不是对外营销承诺，而是运营后台与客户工作台共享的真实项目进度。
- 客户可免费建立项目与问卷草稿，不需要管理员批准“创建”。非问卷研究简报由客户提交进入 `Submitted for review`；样本招募或研究支持问卷也会先进入该状态。管理员确认范围后将项目置为 `Quote required`，再发送正式报价。
- 管理员在 `Client projects` 中录入币种、金额、范围、有效期和可选条款。发送报价会创建可版本化记录，并把项目置为 `Quote sent`；新报价会替代尚未回应的旧报价，避免客户按过期版本确认。
- 客户通过工作台的报价弹窗接受或拒绝；报价邮件只作为回到已登录工作台的提醒入口。接受会留存账户、报价版本和时间，并使项目进入 `Client accepted`。当前不接入线上收款；管理员只应在款项确认后手动设为 `Funded`，再进入招募与上线。因此“接受报价”绝不表示“已付款”。
- 已新增两端不同的站内通知铃铛。客户端接收报价、资金确认、招募、上线与完成通知；管理员接收新项目、项目提交、问卷审核、报价接受或拒绝等运营通知。报价发送同时尝试发送邮件提醒；本地环境未配置投递凭据时，不影响站内通知或项目状态。
- 问卷内容审核与商业阶段严格分离：自行分发问卷审核通过即发布；需要平台样本或研究支持的问卷审核后只进入 `Content approved · awaiting launch`，不收集答卷。仅当项目已进入 `Live` 时，后台才会开启已批准问卷的收集。未通过内容审核的问卷不能被项目状态直接上线。
- 新增 `BusinessProjectQuote` 与 `Notification` 数据模型、迁移文件和可重复执行的本地 SQLite 建表脚本 `npm run schema:business-quotes`。已有本地数据库未写入 Prisma 迁移历史时，应使用该幂等脚本，不要强行运行会要求基线的迁移命令。
- 新增验证 `npm run verify:business-commercial-workflow`，覆盖报价、客户接受、资金闸门、内容审核和受控上线。前端 `npm run build`、Business 工作台验证、问卷验证、商业流程验证与支持知识库验证均通过；仅保留既有包体积提示。
- 前后端已提交并发布。生产数据库已补齐 Business 工作台所需的兼容字段；后续发布仍应先执行对应的幂等建表/补列脚本，再切换应用版本。
- 研究者工作台在发布后继续做了视觉收口：短标题使用展示衬线，其余工作台文字、字段与操作均使用无衬线；左侧重复的联系销售入口已移除；通知在研究者端以居中独立浮层显示；头像菜单可进入 Account；账户页面不再展示登录 IP 或登录地区。Community 仍是登录后可查看的前端预览，尚未开放为公共互动功能。
- 下一步若接入真实支付，应以受控支付页和付款回调驱动 `Funded`，不能把前端按钮或邮件回复当作付款成功；接入前还需确认账单、税务与退款规则。
