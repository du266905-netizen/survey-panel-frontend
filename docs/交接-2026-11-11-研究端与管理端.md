## 三、接口：前端只接了 4 个，缺 3 个客户动作

前端已经调用、后端未实现的：

```
POST  /api/business/projects/:id/contract/send
POST  /api/business/projects/:id/questionnaire/submit-review
POST  /api/business/projects/:id/report/send
PATCH /api/business/projects/:id/report   （APPROVED 发布 / REVOKED 撤回）
```

缺的三个，前端已经接好入口，后端一通就能用：

| 缺的接口 | 客户卡在哪 | 前端状态 |
|---|---|---|
| `POST /contract/sign` | 合同发出去客户签不了，项目停在“合同已发送”，到不了付款 | 卡片/详情已有「签署合同」，点了 404 提示「这一步还没开通」 |
| `POST /questionnaire/client-approve` | 请客户确认问卷，客户没有确认按钮，回收开不了 | 已有「确认问卷」 |
| `POST /accept` | 报告交付后客户无法验收，单子关不掉 | 已有「验收报告」 |

三个按钮都走真实接口，接口一通就不用再改前端。

`report/revoke` 不是单独接口，撤回走 `PATCH /report` 传 `REVOKED`。

## 七、后端必须自测的（前端证明不了）

1. **越权**：用 A 的 token 请求 B 的 projectId / 报告 / CSV / 问卷结果，必须 403 或 404，不能返回数据。
2. **付款金额**：`POST /projects/:id/payment` 实际扣款必须等于报价页展示的合计；前端算的价只是展示。
3. **付款回跳**：PayPal 回跳调的是充值 capture，项目付款要靠 webhook 落 `FUNDED`；两者不能混。
4. **客户三动作的状态机**：sign / client-approve / accept 的前置状态必须后端校验，不能只靠前端按钮。
5. **报告放行语义**：`APPROVED` 与 `SENT` 都算已放行，撤回是 `PATCH /report` 传 `REVOKED`。
6. **配额**：发布后配额是否真正限流（前端只能配置，不能拦截）。
7. **通知**：报告发布后是否产生站内通知/邮件（前端只读通知，不生成）。
8. **客户端事件 → 管理端通知**（客户删除项目等）：见 `docs/待办-后端-2026-11-11.md`，前端铃铛已就绪，只等后端生成。
